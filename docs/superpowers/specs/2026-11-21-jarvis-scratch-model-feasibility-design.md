# JARVIS Scratch-Model Feasibility Prototype

## Status and purpose

This design covers the first project in the JARVIS independence effort: a
bounded feasibility prototype for training and running a small language model
whose weights start from random initialization. It does not yet migrate the
running assistant, change `jarvis\config.py`, add an Android client, or attempt
production-scale training.

The prototype must produce evidence about the training pipeline, offline
inference, model quality, resource needs, and scaling costs before any larger
training run is approved. It is not expected to produce a generally capable
assistant.

## Goals

- Train a small English decoder-only Transformer from random initialization.
- Train its tokenizer vocabulary from the approved corpus; use no pretrained
  tokenizer vocabulary, model weights, or embedding model.
- Keep training dependencies isolated from the normal JARVIS installation.
- Record enough inputs and metrics to reproduce and evaluate a run.
- Export a checkpoint that loads and generates text on the intended upgraded
  Windows PC with networking blocked.
- Establish explicit evaluation and spending gates before scaling.

## Non-goals

- Matching ChatGPT, Gemini, or other large general-purpose assistants.
- Replacing current provider adapters or changing the running JARVIS
  configuration.
- Fine-tuning or distilling another model, or using AI-generated training
  material.
- Building a complete desktop/mobile user experience.
- Automatically renting compute, starting cloud jobs, or incurring charges.

## Project sequence

1. **Feasibility prototype (this design):** build and measure the isolated
   training-to-offline-inference pipeline.
2. **JARVIS app migration:** after a successful review, replace hosted provider
   selection and adapters with the approved local JARVIS runtime. Preserve
   registered tools, confirmation handling, and conversation behavior.
3. **Android client:** design a separate client for a secured local connection
   to the Windows inference host.
4. **Scale decision:** only after prototype results and a separate user
   approval, select a larger corpus, compute plan, local hardware, and budget.

Each later project requires its own design and approval.

## Prototype components

Keep the prototype under an optional `jarvis\training\` package or an equivalent
isolated module, with training-only dependencies not required to run ordinary
JARVIS. Separate operations should cover:

1. **Dataset validation:** read a manifest for every input corpus and validate
   source, license, checksum, and expected files before use.
2. **Tokenizer training:** create a vocabulary from the approved corpus with no
   imported pretrained vocabulary.
3. **Model training:** initialize all model weights randomly and train a small
   decoder-only Transformer.
4. **Evaluation and export:** evaluate against held-out text, save a checkpoint
   and metadata, then run a local offline load/generation check.

The pilot's parameter count and corpus volume are intentionally not fixed by
this design. The first implementation must estimate bounded choices from
available compute and storage, present those choices and costs, and wait for
approval before any rented-GPU job starts.

## Data flow and artifact layout

```text
approved corpus + license manifest
    -> validation, checksums, and train/validation split
    -> tokenizer vocabulary trained from corpus
    -> random model initialization and training
    -> held-out evaluation
    -> checkpoint + tokenizer + run metadata
    -> offline load and generation test on target Windows PC
```

Keep corpora, checkpoints, tokenizer files, and run outputs out of source
control. Store a manifest with each run containing at least:

- corpus identifiers, source URLs, licenses, and checksums;
- preprocessing and split configuration;
- tokenizer configuration and vocabulary checksum;
- model configuration and explicit random-initialization record;
- random seed, training settings, software versions, and run timestamps;
- training and held-out losses, evaluation results, and export details.

The prototype must not silently use a pretrained checkpoint, a network model
download, or another provider when an input or checkpoint is missing.

## Data, privacy, and licensing

- Use only public or appropriately licensed English text whose source and
  license can be recorded and checked.
- Exclude private conversations, personal data, credentials, JARVIS application
  source, and outputs generated by other AI systems.
- Deduplicate and split the corpus before training; held-out evaluation text
  must not be used for optimization.
- Do not automatically turn downloaded web content, user memory, or tool
  results into training data.
- Any rented-GPU operation is user-controlled. No provider is selected and no
  job or bill is authorized by this design. Before a run, the user reviews the
  provider, retention terms, exact approved inputs, estimated maximum spend,
  and whether any training artifacts leave the user's control.

## Offline and online behavior

The prototype has no hosted inference path. The exported JARVIS checkpoint is
the only model used in its offline generation test. That test must run with
network access blocked and fail explicitly if model or tokenizer files are
missing or invalid; it must not fall back to an API.

In the eventual assistant, online web/search tools remain separate from model
inference. They may retrieve current information when the user is online, but
they must not send prompts to an AI service. Offline behavior must not depend on
web access. The current assistant's provider configuration remains unchanged
until the separately approved app-migration project.

## Evaluation and go/no-go gates

The prototype is technically successful only if all of these are true:

1. Model initialization is demonstrably random and no pretrained model or
   embedding artifacts are loaded.
2. A fixed-seed run is repeatable with recorded corpus and configuration
   checksums.
3. Held-out loss is finite and improves over the same model's untrained
   baseline.
4. The exported checkpoint and tokenizer load and generate a non-empty output
   with networking blocked.
5. The report records held-out loss, results on a fixed assistant-prompt set,
   peak memory, generation latency, and the target PC configuration.
6. Tests verify manifest/license rejection, initialization provenance,
   checkpoint round-trip, and offline loading. A small deterministic fixture
   exercises the training path without requiring a rented GPU.

Passing these checks proves that the pipeline works; it does not prove broad
assistant competence. The report must separate training progress from answer
quality and state limitations plainly.

No larger training run may begin until the user reviews the prototype report
and separately approves the target capability, corpus, hardware, provider,
and maximum spend. If the target PC cannot run the exported model within
user-approved memory and latency limits, the scale decision must stop and
return for hardware/design review.

## Errors and safety

Invalid or missing license metadata, corpus checksum mismatches, malformed
training inputs, unsupported hardware, non-finite training metrics, corrupt
checkpoints, and offline-load failures must be explicit errors. Do not silently
skip data, claim success, switch models, or enable network fallback.

Training tools must not execute downloaded corpus content. Training and model
loading are separate from JARVIS tool execution; generated text is never
interpreted as Python, shell commands, or user confirmation.

## Follow-up projects

The later app migration will remove `JARVIS_LLM_PROVIDER`, provider API keys,
and hosted provider adapters only after a local runtime is selected and
verified. It will also replace the pretrained sentence-transformer retrieval
dependency with non-neural local text search if the requirement remains that
JARVIS use no other AI model. The Android client and production-scale model
training remain out of scope until separate reviews.
